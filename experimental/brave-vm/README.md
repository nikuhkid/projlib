# Brave inside Chrome: isolated experiment

The target is the actual 64-bit Brave browser, including its native Shields and Brave Sync UI, executing on the visitor's computer inside a WebAssembly Linux guest. Wolfie supplies the network relay. This is separate from Scramjet rewriting and from the older browser running on Wolfie and streaming frames.

This directory is not part of the published Pages build or the installed host. The candidate runs the pinned official Brave binary inside a 64-bit QEMU WebAssembly guest with Chromium's sandbox enabled. The user explicitly accepted continuing the prototype after observing roughly eight minutes of cold startup. Brave and Brave Sync remain requirements.

Pinned inputs:

- container2wasm v0.8.5, source `087c313479d51cdf255e4f28ded6ae7d8141297b`.
- Its pinned QEMU Wasm revision `8604ed49a3cde392890b014a8d5a959c8a2fe72a`.
- Official Brave amd64 DEB 1.100.58, SHA-256 `2d9d1e664efd60343c77324c836be402cbe57ce12549975584dfa7d073f156a5`.

The guest runs as an unprivileged browser user. The startup command does not disable Chromium's sandbox. No personal profile or Sync chain is included in the guest image. The local graphical display is intended to stay inside the guest and visitor's Chrome; it must not be relayed through Wolfie as a substitute for local execution.

The compiled candidate is approximately 1.08 GB of guest data plus 41 MB of WebAssembly. It is not checked into Git or added to the Pages artifact. The probe server binds only loopback and supplies the cross-origin isolation headers needed by the threaded runtime.

Local verification found two signed-pointer defects in the generated 3 GiB runtime: libffi heap indices sign-extended addresses above 2 GiB, and QEMU's JIT used signed DataView offsets. `patch-runtime.mjs` accepts only the reviewed original loader hash, preserves the upstream file and records the resulting hash and corrections. Tests cover high-bit pointer values without allocating a multi-gigabyte fixture. With this patch Linux boots. The baseline CPU configuration stalled before `brave-browser --version` returned; `qemu64,+rdrand` successfully executed the official binary and reported Brave Browser 158.1.100.58.

The default probe now supplies the Wasm counter's 1 GHz frequency before the kernel's `--` separator. Linux confirms switching to `tsc`; without this correction, calibration failed and the guest used `refined-jiffies`. The graphical server uses `-noshm` because the pinned tiny kernel does not implement SysV shared memory. Startup tracing also found expensive Type 1 font parsing; the probe uses the image's Liberation families. The native Brave toolbar has been visually verified inside the visitor's Chromium tab. Actual Brave also rendered controlled HTML inside the Wasm guest through the guest-only DevTools diagnostic in 240 seconds. Graphical navigation and Sync pairing still require separate checks.

The native Windows networking helper passed ARP, DNS and a real TCP/HTTP request to a public IP-reporting endpoint directly from Wolfie. Node-side tests cover password verification, a fixed twelve-hour deadline, logout disconnection, packet fragmentation and public-web-only egress. The host network stack is a separate per-session process and has no configured host-loopback NAT. Guest TCP is restricted to public destinations on ports 80 and 443; only virtual-gateway DNS and DHCP are allowed over UDP.

An actual Wasm guest also completed DHCP, DNS and a certificate-verified HTTPS request to `api.ipify.org` through the authenticated native relay in approximately thirty seconds. That test used a disposable lab password, temporary loopback listeners, and no Cloudflare. The response address was not retained in the evidence. This validates the guest's transport separately from Brave rendering.

`desktop/start.sh` and the Linux helper are injected through the guest's existing 9p mount. The display bridge carries RFB over the local emulated serial console; `GuestDisplayChannel` creates no network socket. RFB screen and keyboard payloads must never enter evidence logs. The display client is bundled from pinned original noVNC 1.6.0 source; its source archive, MPL notice and bundled dependency notices are retained next to the generated client.

Local profile snapshots are implemented behind `profile=1`. The guest helper pauses the guest's Brave processes, exports regular profile files and recovery journals, and resumes those processes even if export fails. Caches, symlinks and sockets are omitted. The frontend compresses the archive with the browser's native compression stream and atomically stores the current and previous checkpoints in IndexedDB. Profile archives never go to Wolfie. Restore rejects traversal, links, special files, oversized archives and duplicate files before replacing a previous profile. The prototype limits an uncompressed snapshot to 256 MiB.

The full storage fixture passed export, complete Chromium shutdown, a fresh Chromium process using the same dedicated test profile, and restore into a new Wasm guest in approximately forty-three seconds. Binary cookie fixtures, recovery-journal fixtures and font-cache fixtures survived. An actual blank Brave profile was also checkpointed, the outer Chromium process was completely stopped, and the archive was imported by a fresh guest under a fresh Chromium process at the same dedicated test origin. The Go helper's Linux tests cover unsafe archives, previous-profile preservation and pausing/resuming only a selected fixture process. Actual account-cookie survival and Sync pairing remain unverified. Do not enter a personal Sync chain until those checks and the intended host installation are ready.

The local input bridge now uses acknowledged records of at most 256 raw bytes to avoid overrunning the emulated terminal. A synthetic 12,800-byte fixture passed through the actual browser, emulated serial console, Linux TTY and Go display bridge byte-for-byte in approximately forty seconds. This fixture uses no Brave account or real keyboard input.

A later graphical test exposed repeated slash characters when a slow press/release round-trip interacted with X11 autorepeat. The channel now batches adjacent noVNC sends so a tap's press and release can share one record. Guest x11vnc keeps server autorepeat disabled through the long startup instead of [reenabling it after five idle minutes](https://github.com/LibVNC/x11vnc/blob/0.9.16/src/help.c). The viewer handles held-key repeats. The complete synthetic input fixture passed again after this change; that does not by itself verify typing inside Brave.

The corrected graphical guest has rendered Brave's new-tab page, including its background and controls. End-to-end X11 navigation remains too delayed to call this a usable browsing session. A lighter local canvas path now renders a controlled HTML page and has passed actual mouse and keyboard input: the native Brave DOM contained the exact synthetic text typed through the outer canvas. This path uses headless Brave with outer navigation controls, rather than displaying the native OS toolbar. Neither its pixels nor its input travel through Wolfie.

`desktop/canvas.sh` starts actual Brave with a loopback-only DevTools endpoint inside the guest. The Go helper bridges that endpoint over local emulated serial to `probe/browser-canvas.mjs`; it does not expose DevTools on Wolfie. The native CI control verifies both controlled HTML and the actual Brave Sync component with the sandbox enabled, without entering a Sync chain. This passed in approximately six seconds. Sync inside the emulated guest and actual pairing remain separate checks.

The first canvas run passed the page/input fixture, saved a local profile checkpoint, then exhausted the fixed 3000 MiB Wasm heap during further navigation at approximately twelve minutes. Increasing the heap only in JavaScript was rejected by the compiled Wasm memory maximum. Reducing the reserved translation cache from 500 MiB to 128 MiB did not reach the guest's DevTools endpoint within its five-minute wait after restoring the interrupted profile. A blank guest did reach the controls in approximately six and a half minutes. The internal startup check now allows fifteen seconds per HTTP request and ten minutes overall, widening the cold-start window without claiming that the timeout alone caused the earlier failure.

`patch-heap-import.mjs` provides another opt-in comparison for the exact reviewed tuned Wasm artifact. It preserves the original, raises only the shared-memory import maximum from 48000 to 57344 pages, and validates the resulting module. The loader uses a fixed 3584 MiB heap under `--extended-heap`; memory growth remains disabled. Executable instructions, guest RAM and the translation cache remain unchanged. Original and changed SHA-256 values accompany the candidate, and tests reject import-layout drift and verify that other bytes are preserved. This is an experimental allocation comparison, not a confirmed stability or speed fix. All twenty-three Node regression checks pass with loopback networking available. The experiment is not installed or included in the Pages build.

The extended-heap canvas run passed actual Brave HTTPS browsing through Wolfie: the rendered IP-reporting page matched Wolfie's independently checked egress, returning only a boolean to the harness. It ran for fifteen minutes without the earlier emulator allocation crash, then passed controlled close and a final local profile checkpoint. A completely new outer Chromium process read that checkpoint and verified `SessionEnded`; the compressed blank-test profile was approximately 21 MiB. This is bounded runtime evidence, not a general stability guarantee or an account-login test.

Native Sync remains the current blocker. Its correct route and HTML scaffold appear inside the guest, but the `settings-ui` custom element remained uninitialized and the Brave Sync component was absent. A fixed command took 1688 ms in an idle smaller-cache run and 45235 ms during settings initialization in the extended-heap run; these are observations under different load, not a controlled speed comparison. Both normal and `--jitless` native CI controls initialize the actual Sync component. The interpreter-only emulated guest also failed to initialize Sync within approximately five minutes of navigation, and diagnostic commands timed out. Navigating back to the controlled HTML fixture worked. That mode also affects JavaScript/WebAssembly capabilities and remains an optional diagnostic, not the default. No personal Sync chain, credentials or account has been entered.

The browser-facing relay socket can now reconnect after host verification without recreating the guest. A complete runtime test passed initial certificate-verified HTTPS, advanced only the isolated relay's injected clock beyond twelve hours, confirmed that the old grant disconnected its native helper and could not reconnect, then verified again and completed a second HTTPS request in the same guest. The test took approximately forty seconds. Existing TCP connections can fail during a relay restart; applications may need to retry. The server does not extend an existing grant automatically.

The isolated probe includes host verification controls. They clear the password after submission, retain no password in web storage, disable guest startup until verified, and reconnect a running guest only after verification. Browser checks cover rejection, login, logout and re-verification. These controls are not installed in the live ProjLib Host.

`Save and close Brave` sends SIGTERM to the guest's browser main process, waits for its writers to stop, and then checkpoints its profile. It does not kill unrelated guest processes or host applications. A Linux fixture verifies that the selected process flushes data and an unrelated process remains alive. This also passed with actual Brave. After completely restarting outer Chromium, a read-only inspection of the saved blank profile found `SessionEnded`, which [Chromium distinguishes from a crash](https://chromium.googlesource.com/chromium/src/+/lkgr/chrome/browser/sessions/exit_type_service.cc). A separate close capability prevents offering this control with older helpers. Killing an entire guest without closing Brave first produced an unclean-exit prompt during the earlier restore check.

The translator comparison was built separately with a warmup threshold of 100 instead of 1500 and a generated-module limit of 60000 instead of 15000. All thirteen artifact checksums passed and its unpatched JavaScript loader was byte-identical to the reviewed baseline. The original `--dump-dom` probe still did not complete within ten minutes, and a native control using those startup settings also timed out after ninety seconds. A separate native DevTools control rendered the controlled HTML in four seconds with the sandbox enabled. The guest-only DevTools probe then rendered that HTML inside Wasm in four minutes. The probes differ, so these results do not establish a speedup over the baseline translator.

`--bounded-io` is an additional opt-in investigation of the [upstream terminal polling report](https://github.com/ktock/qemu-wasm/issues/28). The loader scans all descriptors without blocking before waiting, caps the remaining poll wait at ten milliseconds, and corrects another signed heap pointer in the terminal's atomic wait. Scanning first matters: an empty TTY must not prevent checking ready network descriptors. The guest uses explicit 9p devices with `ioeventfd=off`. This configuration passed real guest DHCP, DNS and certificate-verified HTTPS in approximately fifty seconds. This is transport validation, not a claim of faster Brave rendering. The baseline polling workaround remains available for comparison.

The bounded-I/O profile fixture also passed a complete outer-browser restart and fresh guest restore in approximately fifty-nine seconds. Its rendering diagnostic binds DevTools only to `127.0.0.1:9222` inside a blank disposable guest; this endpoint is absent from the regular graphical startup and is never exposed on Wolfie. The diagnostic returns only a fixed pass marker after reading the controlled HTML's expected text. It rejects persistent-profile mode.

```powershell
node experimental/brave-vm/build-viewer.mjs
node experimental/brave-vm/run-profile-roundtrip.mjs .local/full-browser/engine-candidate
node experimental/brave-vm/run-probe.mjs .local/full-browser/engine-candidate --input-probe --duration-seconds 150
node experimental/brave-vm/run-probe.mjs .local/full-browser/tuned-engine-candidate --render-probe --bounded-io --duration-seconds 600
node experimental/brave-vm/run-probe.mjs .local/full-browser/tuned-engine-candidate --browser-canvas --persistent-profile --browser-profile .local/full-browser/brave-browser-canvas-fixture --probe-port 9480 --bounded-io --tb-mib 128 --linger --duration-seconds 1200 --network-helper .local/full-browser/canvas-candidate/ProjLibBraveRelay.exe
node experimental/brave-vm/run-reconnect-probe.mjs .local/full-browser/engine-candidate .local/full-browser/input-fixture-candidate/ProjLibBraveRelay.exe
node experimental/brave-vm/run-auth-probe.mjs .local/full-browser/engine-candidate .local/full-browser/input-fixture-candidate/ProjLibBraveRelay.exe
node experimental/brave-vm/run-probe.mjs .local/full-browser/engine-candidate --desktop --persistent-profile --browser-profile .local/full-browser/brave-browser-sync-fixture --probe-port 9476 --linger --duration-seconds 1200 --network-helper .local/full-browser/input-fixture-candidate/ProjLibBraveRelay.exe
```

The interactive probe accepts `snapshot`, `screenshot`, `navigate-sync`, `navigate-example`, `paste-sync`, `paste-example`, `physical-sync`, `physical-example`, `click-guest X Y`, `press-escape`, `save-profile`, `close-profile`, and `stop` on stdin. `probe-controls.mjs` is reloaded for these fixed lab actions so a long-running test need not reboot for a control change. Use `close-profile` and wait for success before `stop` when testing normal profile restoration. Start it in a terminal with stdin open. Reuse both the dedicated browser-profile directory and the probe port to test profile restoration across complete outer-browser restarts. Runtime evidence belongs in the ignored `.local/full-browser/evidence` directory. `--trace` and `--debug-processes` are disposable-profile diagnostics; never enable them with a personal profile. The optional Debian strace diagnostic is not installed on Wolfie.

For the separate larger-heap comparison, run `node experimental/brave-vm/patch-heap-import.mjs .local/full-browser/tuned-engine-candidate` once, then add `--extended-heap` to the canvas probe without changing `--tb-mib`. The checked helper from the startup candidate uses the widened DevTools wait. Add `--jitless` only for the optional interpreter comparison. These controls do not affect production. Canvas fixture actions include `canvas-fixture`, `type-fixture`, `verify-fixture`, `latency-fixture`, `inspect-sync`, `inspect-settings-load`, `inspect-settings-script`, `refresh-canvas`, and `check-home-egress`. The egress action returns only a boolean; do not take screenshots of its IP-reporting page.

The final design must provide authenticated relay access with the existing twelve-hour verification requirement, public-destination restrictions, local persistent profile storage, and a direct connection to Wolfie with no Cloudflare fallback. Direct access to the No-IP endpoint previously failed on the work network; changing the browser engine cannot establish reachability to a blocked relay address.
